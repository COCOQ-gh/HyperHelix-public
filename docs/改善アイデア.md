# HyperHelix 改良アイデア

目的: HyperHelix の堅牢さを保ったまま、日常運用の軽快さを上げるための案を整理する。
ここに書く内容は実装予約ではなく、次回以降の `/helix` や `/cycle` でタスク化するための候補である。

## 方針

HyperHelix の強みは「5フェーズを省略しない」「検証してから完了を主張する」「経験を次回へ渡す」ことにある。
したがって軽量化は、フェーズを削る方向ではなく、記録・検証・D7 の機械化によって人間/AI の手書き負荷を下げる方向がよい。

## 優先候補

### 1. brief generator

**分類: ツール改善**(通常の `/helix` タスクで進められる)

`node tools/hyperhelix.mjs brief --task TASK-YYYYMMDD-NNN --mode standard --title ...`
のようなコマンドを追加し、タスクブリーフの初期作成を自動化する。

> レビュー所見(2026-06-19): 単なるテンプレコピーの省力化は価値が薄い。本当の価値は
> concurrency.md §2 の **ID claim 規律(次の空き NNN を確保・衝突時バンプ)を機械化**できる点。
> そこを主目的に設計する。出力先は構造問題A(機械可読アンカー)に従う。

期待効果:
- テンプレコピー、タスクID記入、日付、project/genre、深度モード、フェーズゲート欄の初期化を省力化できる。
- 空欄テンプレのまま進む事故を減らせる。
- R6 の context 判定や framework-only 連続数の記入補助も将来組み込める。

注意点:
- 自動生成は証跡の代替ではない。要求定義・受入条件・検証計画の判断は残す。
- 既存ブリーフを上書きしない。既存 ID があれば失敗する。

#### active scan 除外設計

active scan は **現役説明の drift 検出**であり、歴史記録や検出仕様そのものを罰しない。
docs/ 全体は原則対象にするが、以下の順で除外・弱化する。

1. **対象集合**
   - `README.md`
   - `docs/**/*.md`
   - `assets/**/*.md`
   - `core/**/*.yaml`
   - `AGENTS.md` / `CLAUDE.md` / `.claude/commands/*.md`
   - `tools/**/*.mjs` は旧語を文字列リテラルとして持つ可能性があるため、最初は warning のみ。

2. **歴史記録除外**
   - `amendments.md` と `tasks/**` は既定で除外する。
   - 理由: 過去時点の判断・旧語・失敗事例を監査ログとして保持するため。
   - 例外: 将来 `tasks/` テンプレ本体を置く場合は、`assets/templates/` 側を対象にし、過去 task は対象にしない。

3. **DEPRECATED マーカー除外**
   - ファイル先頭20行以内に `DEPRECATED` を含むファイルは、ファイル単位で active scan から除外する。
   - 既存例: `assets/workflows/theta-review.md`、`core/dictionary.yaml`。
   - `deprecated` の小文字表記も検出対象にしてよいが、除外の正規マーカーは大文字 `DEPRECATED` に寄せる。
   - 除外しても validate の通常構造チェック対象から外すわけではない。旧語 scan だけを抑制する。

4. **例示・引用ブロックの扱い**
   - fenced code block 内の旧語は既定で除外する。
   - Markdown blockquote (`> ...`) 内は既定で warning 抑制候補にする。ただし「現役手順として引用している」可能性があるため、初期実装では info レベルに落とす。
   - 検出仕様を説明する文書では、次のアンカーで範囲除外できるようにする。

```md
<!-- HH:ACTIVE-SCAN-ALLOW reason="example of deprecated terms" -->
PATTERN.* / tasks_since_tuning / recompute --write
<!-- /HH:ACTIVE-SCAN-ALLOW -->
```

5. **判定レベル**
   - active 本文の禁止語: error。
   - `docs/` の設計メモや引用で文脈が曖昧なもの: warning または info。
   - allow ブロック内: no issue。ただし allow ブロック自体が多すぎる場合は別 warning。

6. **失敗時の出力**
   - `file:line`、検出語、分類(active/deprecated/history/example)、推奨対処を表示する。
   - 推奨対処は「現役文言なら更新」「歴史記録なら除外対象へ移動/マーカー付与」「例示なら allow ブロックで囲む」の3択にする。

7. **自己適用（dogfood）の注意**（レビュー点6）
<!-- HH:ACTIVE-SCAN-ALLOW reason="point 7 explains self-application and must name the terms" -->
   - 本文書(改善アイデア.md)自身が検出語 `PATTERN.*` / `PRINCIPLE.*` / `OBSERVATION.*`(line 64 近傍)・
     `tasks_since_tuning` 等を**検出仕様として**含む。対象集合(point 1: `docs/**/*.md`)では
     スキャンが**自分の仕様書を flag** する。これは設計どおりで、本文書は point 4 の
     `HH:ACTIVE-SCAN-ALLOW` ブロックで該当箇所を**自己 dogfood で囲う**こと。実装タスクの受入条件に含める。
<!-- /HH:ACTIVE-SCAN-ALLOW -->
   - info レベルの新設は現 validator の2値出力(error/warning)へ第3段を足す。exit code 方針
     (info は exit 非ゼロにしない等)を同時に配線する(AP-003: 宣言と消費側を同時に配線)。

### 6. finish command

**分類: ツール改善**(高価値。案2+3+validate のコンポーズ。案2の後に実装)

validate、秘密スキャン、D7 自動更新、明示パス staging、commit message 下書きをまとめる
完了オーケストレーションコマンドを検討する。

例:

```powershell
node tools/hyperhelix.mjs finish --task TASK-20260618-004 --use N-011
```

期待効果:
- 完了処理の順序ミスを減らせる。
- 秘密スキャンを忘れにくくなる。
- コミットメッセージの検証行を実行結果から作れる。

注意点:
- D7 自動更新込みのため、案2(D7 auto-summary)とブリーフアンカー化が実装済みであることを前提にする。
- 実際の `git commit` は `--commit` 明示時だけにする、または下書き出力に留める。
- staging は explicit paths のみ。`git add -A` は使わない。

> レビュー所見(2026-06-19): 秘密スキャン忘れ(HH-019)を直接防ぐ高価値案。**fail-closed 必須** —
> 秘密ヒットや validate エラーで全体を中断し、コミットは行わない。案2(D7)・案3(スキャン)・既存 validate の
> コンポーズなので、それらの後に capstone として実装する。finish は **D7 自動更新込み** とし、
> D7 なしの軽量版は別コマンドに分けない。

**操作順序の固定**（レビュー点2: 不可逆操作と中断可能チェックの分離）:

finish は内部に**不可逆操作**(`task_index +1` の bump)を含む。bump 後・commit 前に失敗すると
**カウンタだけ進みコミットが無い drift** が起きる。これを防ぐため操作順を固定する:

1. 中断可能チェックを**全て先に**通す: `validate`(0 error)→ 秘密スキャン(ヒット0)→ 明示パス staging。
2. ここまで全通過した場合のみ、不可逆ゾーンへ入る: bump(`task_index +1` ＋ note strength)→ ブリーフ D7 更新 → `git commit`。
3. 不可逆ゾーンで失敗した場合は、進んだカウンタと commit 状態を必ず報告する(サイレントな drift を作らない)。

要するに「**壊れても良い検証を先に、戻せない記録を最後に**」。fail-closed が「何で止めるか」なら、本ルールは「いつ戻せない操作に入るか」を定める。

**bump の冪等化（Codex レビュー所見・高）**: 現 `bump` は `task_index` を現在値から無条件に +1 する
([tools/hyperhelix.mjs:261-269](tools/hyperhelix.mjs:261) — taskId 重複チェックなし)。finish が
不可逆ゾーンで中断し**再実行**されると、bump が再度走って `task_index` が**二重加算**される。
操作順序の固定だけでは塞げない別の穴。
→ **bump を taskId で冪等化する**: 同一 taskId の bump は1回だけ効かせる(直近 commit 済み taskId、
または `task_index` 行の `# +1 <taskId>` コメントを参照して、同一 taskId の再 bump は no-op)。
finish はこの冪等 bump を呼ぶ。concurrency.md §3(累積カウンタは base+Σδ)とも整合させる
(冪等性は「同一 taskId の δ を二重計上しない」こと)。

## レビュー所見 — 構造的問題(2026-06-19)

個別案の前に、複数案にまたがる2つの構造的問題を先に解く必要がある。

### 構造問題A — ブリーフのフォーマット依存(案1・2・6 に共通)

案1(生成)・案2(D7 書き戻し)・案6(finish)はいずれも**ツールがブリーフ Markdown を読み書きする**。
しかし現ブリーフは見出し語・列順に依存した自由 Markdown で、HH 改定のたびにテンプレが変わる
(D7 欄は HH-016 で書き換わった実績)。見出しテキスト頼みの編集ツールはテンプレ改定で
**サイレント破損**する(AP-003 の裏返し)。

→ **未着手の前提作業**: ブリーフに機械可読アンカーを入れ、ツールはアンカー内だけを編集する。
これを案2の前にやらないと案2・6 は保守不能になる。

#### ブリーフアンカー粒度の設計

アンカーは「ツールが編集する単位」と「人間/AI が自由記述する単位」を分けるために使う。
見出し名や表の列順ではなく、固定アンカー名を API とみなす。

**v1 最小アンカー集合**（レビュー点5: ツールが**反復書き込み**する領域だけをアンカー化する。
生成1回 or 手動の領域は v1 ではアンカー化しない — 8領域一律はテンプレを重くし「軽量化」目標に逆行する）:

| アンカー | 対象 | 主な利用コマンド | 編集方針 |
|---|---|---|---|
| `HH:BRIEF_META` | task id / 日付 / project / depth / execution mode / 委任状態 | `brief` | generator が初期生成。既存値は原則上書きしない |
| `HH:TASK_LIST` | P1/P2 の task-list | `brief`, 将来の status updater | 行単位更新。未知列は保持 |
| `HH:EVALUATE` | V1/V2 の検証結果表 | `finish` | validate / secret scan / user-specified checks の結果だけ更新 |
| `HH:D7` | counter / note strength / validate / commit checklist | `bump --update-brief`, `finish` | 実行結果から fail-closed で更新 |

**v1 で除外する領域**（レビュー点3・4反映）:
- `HH:PHASE_GATE` / `HH:DISTILL`: 生成1回 or 手動。機械アンカー不要。後で必要になれば足す。
- `HH:FRAMEWORK_REVIEW`: R1〜R6 は `/cycle` タスクにしか無く、標準ブリーフテンプレに R1-R6 節は存在しない。
  全ブリーフに置くと通常タスクが空の review 領域を背負う。**cycle 用テンプレ限定の条件付き挿入**とし、標準ブリーフには入れない。
- `HH:COMMIT`: commit message の行き先は git でありブリーフではない。下書きをブリーフに持つと
  実コミットとドリフトする第2の真実になり、自分のコミットメッセージ下書きを自分が内包する循環になる。
  **永続化せず `finish` の stdout に留める**。

アンカー形式:

```md
<!-- HH:D7 version=1 -->
... machine-editable markdown ...
<!-- /HH:D7 -->
```

設計ルール:
- アンカー名は大文字固定。未知アンカーは保持し、validator は warning に留める。
- 同名アンカーが1ファイルに複数ある場合は error。
- 開始/終了アンカーの片欠けは error。
- **version 不一致は fail-closed**（レビュー点1）: ツールは自分が知る version より**新しい** version の
  アンカーを編集せず中断する。これがないと旧ツールが新フォーマットを破壊しうる。version 番号は
  アンカーごとに独立に上げる。未知 version は warning ではなく**編集中断（処理は継続し当該領域のみスキップ）**。
- ツールは対象アンカーが無い場合、勝手に本文を探索して編集しない。`--insert-anchors` のような明示オプションか、brief generator でのみ追加する。
- アンカー内でも未知列・未知行は保持する。更新対象セルだけを書き換える。
- `HH:D7` は実行結果に基づくため、validate 失敗・秘密スキャン失敗・git staging 失敗時は更新を中断する。
- 旧ブリーフ移行は一括変換しない。新規 brief からアンカー付きにし、既存 brief は必要時だけ task 単位で移行する。
- **「アンカー化」作業の実体はテンプレ本体のアンカー化（Codex レビュー所見・中）**: 現テンプレは
  Evaluate / D7 等を見出しベースの自由文で持つ([assets/templates/task-brief.md:117-120](assets/templates/task-brief.md:117) ・
  [:162-169](assets/templates/task-brief.md:162))。実装順 step2 の「アンカー化」は**まず
  `assets/templates/task-brief.md` にアンカーを入れる**こと。これで新規 brief はコピー時にアンカーを継承し、
  generator(案1・step5)が無くても案2/finish が機能する(chicken-egg の解消)。既存 brief は未アンカーのため、
  ツールは「アンカー無し → 本文探索せず no-op」で安全側に倒す。

### 構造問題B — ツール改善と統治変更の混在(案4・5)

## ブリーフ軽量化の策定(2026-06-19)

**分類: ツール改善 + 一部チェックリスト改定**（loop.yaml の required_steps は変えない＝フェーズ不変。詳細は下記の人間ゲート判定）

### 観察(計測)

直近ブリーフは **150〜198 行**(平均 ~180)。テンプレは **21 サブセクション**。重さの主因は儀式と重複であって、証跡そのものではない。アンカー化(BRIEF_META/TASK_LIST/EVALUATE/D7)で機械記入が増えた今、人間/AI が書く部分はさらに削れる。

### 原則(何を削り、何を守るか)

軽量化は**重複・定型・空欄の儀式**を削る。**証跡は削らない**。
- **守る(不可侵)**: S1 intent(何を/なぜ/成功条件/スコープ外)、task-list(acceptance_check 付き)、Execute ログ(実施/結果)、V1/V2 検証結果 + 秘密スキャン(HH-019)、D7 カウンタ/ノート + R6 連続数。原則「証跡は値であって散文ではない」(AP-004)・「空テンプレは証跡でない」(N-004)。
- **削る(対象)**: 他セクションと重複する表、routing.yaml の再記述、新規タスクで自明な定型行、空欄に「なし」を埋めるだけの行。

### 軽量化レバー(具体)

| # | レバー | 内容 | 削減目安 | 種別 |
|---|--------|------|---------|------|
| L1 | **P3 完了条件一覧を撤去** | task-list の `acceptance_check` 列が完了条件そのもの。別表は二重管理。P3(loop の工程=受入基準の定義)は task-list の列で充足する(plan.md に明記) | ~6-8 行 + 同期負債 | テンプレ + checklist |
| L2 | **P5 検証計画を参照化** | 「routing.yaml `by_change_type`: <type>」+ **予定スキップのみ**を列挙。チェック種別の再記述をやめる(スキップこそが証跡) | ~5 行 | テンプレ |
| L3 | **フェーズゲートを1行化** | 「新規 / Search 開始 / 前提不足なし」を1行に。**前フェーズへ戻る場合のみ**フル表(判断が情報を持つのはその時だけ) | ~8 行 | テンプレ + checklist |
| L4 | **空欄セクションは省略(「なし」を書かない)** | S3 不明点 / EX-5 失敗ログ / 失敗帰属 / V3 / D2 は該当時のみ記載。非該当なら**節ごと省略**(「なし」行も書かない) | ~5-15 行 | テンプレ + checklist |
| L5 | **記入例をテンプレ外へ** | 全ブリーフが ~12 行の記入例を毎回携行している。`task-list-schema.md` か専用 reference へ一度だけ置く | ~12 行 | テンプレ |
| L6 | **micro/light 用の短縮テンプレ** | micro の minimum_outputs(objective/change/validation/D7 ≈ 15 行)に対応する**短縮テンプレ**を別ファイルで用意。trivial タスクをフル 200 行テンプレから起こさない。`brief --mode micro` が短縮テンプレを使う | trivial で ~150 行 | ツール + テンプレ |
| L7 | **機械記入を前提に人間記述を圧縮** | BRIEF_META は `brief` 生成、D7 は `bump --update-brief`、V1/V2 は `finish` が充填。人間はアンカー外の intent と task-list に集中 | 体感負荷減 | 既存ツール活用 |

### 期待効果

standard ブリーフを ~180 行 → **~110-120 行**、micro/light を **~15-30 行**へ。証跡密度(検証結果・D7・R6)は不変のまま、儀式と二重管理を除去。

### 人間ゲート判定(構造問題B)

- **ツール/テンプレ/checklist のみ(自動・/helix で可)**: L1-L7 の本体。loop.yaml の `required_steps` は**変えない**——P3 は工程として残り、記録先が task-list の列になるだけ。フェーズは1つも削らない(憲法・ループの公理3と整合)。
- **要確認(微妙)**: L4 で standard の conditional_steps(D2 等)を「非該当なら節省略」とする運用は、現行 loop.yaml の文言(「D2 は Fail 時必須」)と既に整合(Fail なし＝不要)。**新たな amendment は不要**と判断。ただし plan.md/distill.md の文言調整は伴う。

### リスク

- 削りすぎて証跡が薄くなる。緩和: 「守る(不可侵)」リストを checklist に固定し、validate と finish の機械チェック(秘密スキャン・D7・アンカー)は不変。
- 短縮テンプレ(L6)の濫用(本来 standard を micro テンプレで処理)。緩和: micro の use_when は固定語彙(HH-022)。テンプレ選択は深度判定に従属。

### 実装順(案)

1. L1(P3 撤去)+ L2(P5 参照化)+ L3(ゲート1行化)+ L4(空欄省略)+ L5(記入例移設) — テンプレ + plan.md/distill.md の文言調整。1タスク。
2. L6(micro/light 短縮テンプレ + `brief --mode` 連携) — ツール + 新テンプレ。1タスク。
3. 効果測定: 次の数タスクのブリーフ行数を計測し、証跡(V/D7/R6)が落ちていないか確認。

## R7 の設計 — framework-review への systemic レンズ追加(2026-06-19 設計開始)

**分類: 統治変更**(framework-review.md の機構拡張 = amendment 級。実装時に HH 起票)

### 背景(なぜ R7 が要るか)

本セッションの考察で判明: R1〜R6 と AI のレビューは**局所整合**(在るものの正否)は捕えるが、
**系統的な盲点**——①omission(在るべきで無いもの)②cost-without-value(コストが価値に見合うか)
③frame lock-in(枠そのものの是非)——を構造的に見落とす。実際、索引化(amendments 886行が無索引全文必読)と
ROI の洞察は AI のレビューでなく**人間**から出た。R7 はこの systemic レンズを**機構に埋め込み**、
人間が毎回割り込まなくても系統的な問いが構造に乗るようにする。

### 設計原則(チェックリストで盲点を捕える難しさへの対処)

「何か欠けていないか?」は「いいえ」で充足でき無価値(AP-004)。R7 は**判断でなく計測**に寄せる:
各サブチェックは**数値か YES/NO + 根拠**を出す。omission をチェックリストで完全には消せないが、
**omission が隠す具体量(無索引の嵩・青天井の伸び・出力なきコスト)を計測すれば、数値が問いを強制する**。
スタンスは**「初見の読者ならどこを不条理と感じるか」**(作り手の正常化バイアスを外す)。

### R7 サブチェック(改稿 2026-06-19 — Codex 所見反映)

閾値・出典・敵対形を固定し、散文充足(AP-004)と手動計測の楽観を潰す。「必読」の単一権威は
読み込み順(CLAUDE/AGENTS の常時必読 + 索引読み tier)。計測は `cost-report` ツールが算出(下記)。

| # | 名称 | 内容(固定した観測出力) | 何を捕えるか |
|---|------|------|------|
| R7a | 固定費の計測 | `cost-report` 出力の**数値**: 常時必読 tier の総行数 / 標準ブリーフ典型行数。前回 R7 比で +X%。閾値: 単一の必読資材が **300行超** かつ索引/階層なし＝finding | 起動・per-task の肥大(amendments 886行を捕えたはず) |
| R7b | 無索引バルクの検出 | `cost-report` が、全文必読(索引/検索経路なし)かつ **300行超**の資材を列挙。1件でもあれば finding → 索引/階層化を提案。閾値 N=300 を finding 基準として固定 | 辞書-索引テスト(omission) |
| R7c | コスト/成果(外部価値) | 前回 R7 以降のバッチの概算コスト + **外部価値シグナル**(下流で採用された成果物 / 将来コスト削減 / 人間介入の置換 のいずれか具体)。**特定可能な外部価値が無ければ finding**(main でも記録。R6 STOPPED で enforcement は無いが記録は残す)。注: 外部価値の判定は**人間の判断**でブリーフに記録する(`cost-report` はコスト側=行数・大型資材のみを算出。機械検知ではない) | cost-without-value |
| R7d | 敵対的類推・枠 | (a) 支持する類推 + (b) **この設計を棄却する競合類推を最低1つ** + (c) その競合枠で欠ける性質、を記す。**支持類推1つだけでは不充足**(散文充足を排除) | frame lock-in(単一類推は枠固着を温存) |
| R7e | 累積の棚卸し(期限付き) | 前回 R7 以降に増えた必須コスト(新必須フィールド/必読ファイル/常時チェック)を列挙。各々に**価値根拠(防いだ/可能にしたものを計測可能なら数値で)+ 再正当化の期限**。根拠なき「正当」は不可 | 作り手の正常化(茹でガエル) |
| R7f | R7 自身の計測 | R7 実行の overhead(cost-report 実行 + R7 記録行数)を記録。R7 自身が予算超過なら finding(R7 が R7 を測る) | R7 の自己肥大 |

高レバレッジは **R7a/R7b**(索引問題を捕える・ツール裏付け)と **R7d**(敵対類推=再フレーム)。

### cost-report ツール(後続でなく**前提**) — Codex 所見#5

索引見落としは複数ファイル横断の計測(読み込み順の総行数・索引有無・伸び)を要し、まさに R1-R6 が
**手動で見落とした所**。よって `node tools/hyperhelix.mjs cost-report`(常時必読総行数の出力・索引なし
300行超の flag・バッチコスト記録)を **R7a-c の前提**とする(手動計測に頼らない)。

### 配線(実装時に必須) — Codex 所見#1/#6(AP-003)

R7 を framework-review に足すだけでは発火しない。実装時に**同時に**:

### 記録先(テンプレ矛盾の解消) — Codex 所見#8

R7 結果は **/cycle ブリーフ本文のみ**に記録。標準テンプレには R7 欄を**追加しない**(ブリーフ軽量化と整合。
旧『次段』の「テンプレ R7 記入欄」は撤回)。

## 採用判断の基準

- ループのフェーズを削らない。
- 判断は人間/AI が行い、転記・定型更新・検出を機械に寄せる。
- validate で守れるものは validate に寄せる。
- 例外は狭く、条件を固定語彙で書く。
- 軽量化によって秘密スキャン・validate・D7 が抜けないようにする。
- **軽量化は重複・定型・空欄の儀式を削り、証跡(値)は守る**(ブリーフ軽量化の策定)。
