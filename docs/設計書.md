# HyperHelix — 設計書

3つの先行フレームワーク(HelixPDCA / Helix_Reflex / MetaHelix)の統合として HyperHelix を設計した全記録。
本書は人間向け文書であり、運用時にAIが参照する資材ではない。創設裁可は `amendments.md` HH-000。

## 1. 統合の基本方針

全体方針は Helix_Reflex の設計見直し原則を踏襲した:「原則が要求する以上に部品を増やさない」。
3つのフレームワークが重複して持つ機構(ループ・知見昇格・人間ゲート)は各1つに統合し、
それぞれで最も成熟した実装を採用した。

| 機構 | 採用元 | 理由 |
|---|---|---|
| タスクループの工程定義 | MetaHelix | チェックリスト・証跡・例外処理まで運用検証済み(実タスク適用実績あり) |
| Evaluate の明示化・失敗帰属 | Helix_Reflex | カウンタ更新(D7)が Evaluate の P/F 判定を前提とするため |
| 計画の深度モード | HelixPDCA | P0〜P8 を全タスクに課すのは過剰。タスク規模で深さを変える設計が実用的 |
| 知識の昇格・降格 | Helix_Reflex | 整数ゲート・窓評価・アーカイブ主義まで AM-001〜010 で裁可済みの完成形 |
| 人間ゲート | Helix_Reflex | 単一窓口(amendments)が HelixPDCA の supplement より一貫している |
| 検証ポリシー | HelixPDCA | validation-rules.yaml が最も体系的。HyperHelix では routing.yaml に圧縮 |
| 自己改善の畳み込み | Helix_Reflex | メタループを独立機構にしない(公理4の素直な実装)。MetaHelix のレビュートリガーは維持 |

## 2. 三重螺旋モデル

- **実行螺旋**: Search → Plan → Execute → Evaluate → Distill(`core/loop.yaml`)
- **知識螺旋**: observation → pattern → principle → axiom_candidate →(人間)→ axiom、
  project → genre →(人間)→ universal(`core/knowledge.yaml` + `core/gates.yaml`)
- **統治螺旋**: 高影響変更のみ `amendments.md` で人間が裁可

3本は独立した機構ではなく、Distill(D1〜D7)が結節点になる:
実行螺旋の各タスクが D7 でカウンタを更新し、カウンタが知識螺旋のゲートを駆動し、
ゲートが人間承認を要する変更を統治螺旋(HH提案)へ押し出す。

## 3. 設計判断ログ

### D-01 フェーズ数: 5フェーズに統一
- MetaHelix は4フェーズ(S/P/E/D)、Helix_Reflex は5フェーズ(+Evaluate)、HelixPDCA は PDCA。
- **判断**: 5フェーズ。失敗帰属(適用資材への fail+1)は「成果物の機械チェック」という明示の Evaluate フェーズを要求する。MetaHelix では E2(検証)に埋まっていたが、知識螺旋と接続するため独立させた。
- HelixPDCA のマッピング: P0〜P8 → Search S1/Plan P1〜P5 に圧縮、Do → Execute、C1〜C4 → Evaluate、A1〜A5 → Distill。

### D-02 Distill を D1〜D7 に拡張
- MetaHelix の D1〜D6 に **D7(カウンタ更新)** を追加。知識螺旋の駆動源はカウンタであり、更新をフェーズ工程として明文化しないと確実に漏れる(アンチパターン AP-002 として先回りで登録)。
- MetaHelix の improvement-log.md は廃止。役割は task-brief(個別記録)+ knowledge.yaml(再利用知見)+ amendments.md(高影響変更)に分配した。

### D-03 人間ゲートの単一窓口化
- HelixPDCA の supplement.md(AGENTS.md 昇格待ち)と MetaHelix の improvement-log を廃し、Helix_Reflex 方式の amendments.md に一本化。提案IDは HH-NNN。
- ゲート対象は Helix_Reflex の5項目+「憲法の変更」(HelixPDCA の AGENTS.md 読み取り専用則に相当)。

### D-04 .claude/commands/ の許可(AM-ENV の改訂)
- Helix_Reflex AM-ENV は `.claude` フォルダ作成を禁止。一方 HelixPDCA(/pdca)と MetaHelix(/サイクル)はスラッシュコマンドを実運用していた。
- **判断**: `.claude/commands/` を「薄い起動コマンド専用(ルール本体の記述禁止)」として許可。AM-ENV の本旨は「ルールの分散・重複の防止」であり、ポインタ専用なら本旨を侵さない。エントリポイント(AGENTS.md / CLAUDE.md)のポインタ専用則は維持し、ツールの ENTRYPOINT 検査も継承した。

### D-05 言語レイヤー
- ユーザー層(constitution.md / amendments.md)= 日本語、AI層(core/ / assets/checklists ほか)= 英語(Helix_Reflex 方式)。
- タスク記録(tasks/)とユーザー向け文書(README / docs/)= 運用言語(日本語)。MetaHelix のタスクブリーフ実務と HelixPDCA の「採用先プロジェクトの運用言語」則を採用。
- MetaHelix のチェックリスト群は日本語だったが、AI層資材としてレイヤー公理に従い英語へ統一した。

### D-06 知識コーパスと θ の継承
- `core/gates.yaml` は Helix_Reflex thresholds.yaml v1 を逐語継承(裁可済み値の再利用。ゼロから再裁可するより安全)。
- `core/knowledge.yaml` は Helix_Reflex の資材3件とカウンタ(task_index=191)を逐語継承し、HyperHelix 生まれの種資材 OBSERVATION.LOOP.001(フェーズゲート証跡)を1件追加。コールドスタートを「種から育てる」公理の実装。
- 辞書も逐語継承し、universal に phase-gate / evidence、genre に framework(メタ鎖用)を追加。

### D-07 タスクブリーフへの資材トラッキング統合(新規設計)
- MetaHelix のブリーフに「取得資材(S2)」「適用資材ID(E列)」「失敗帰属(V)」の欄を追加。
- これにより D7 のカウンタ更新(retrieved / seen / fail の区別)がブリーフから機械的に転記できる。3フレームワーク統合で生まれた新しい接合部であり、HyperHelix の中核的な改良点。

### D-08 検証ポリシーの圧縮
- HelixPDCA validation-rules.yaml(207行)を routing.yaml の validation セクションに圧縮。変更種別→チェック種別の対応、スキップポリシー(理由・残存リスクの報告義務)、「未実行のチェックを通ったと主張しない」を保持。HelixPDCA 固有のチェッカー契約(check-doc-index.ps1 関連)は HyperHelix に対応物がないため非継承。

### D-09 ツールの移植
- tools/hyperhelix.mjs は Helix_Reflex の helix-reflex.mjs を移植(パス・スキーマ期待値・ブランディング変更、scope_demotion ゲート検査を1件追加)。固定スキーマ専用の検証器・再計算器という性格は不変。
- helix-diagnose.mjs(セッション監査)は初版では非継承。運用開始後、必要になった時点で移植する(未決事項 U-01)。

### D-10 HelixPDCA のユーザー要求精緻化
- u0〜u4 サイクルは独立機構とせず、憲法の実行原則(「曖昧さをユーザーの落ち度として扱わない」「前提を置いて進む」)と Search S1(「1つの簡潔な質問へ変換」)に圧縮した。
