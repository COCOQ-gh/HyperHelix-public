# Review-Only Record — lightweight "look and report" log (HH-023)

A review-only record is for a request that asks ONLY to inspect and report —
producing NO durable artifact change. It is NOT a task: it does not pass the
five-phase loop, does not increment `counters.task_index`, and does not count
toward the R6 framework-only streak. Ratified by HH-023.

This exists so "ちょっと見て" (just take a look) does not carry the same weight
as a real task or a /cycle. The single authority for review-only is this file.

## 1. Strict precondition — session-owned write-set is empty (HH-068)

A session qualifies as review-only ONLY when it performs no repository write of
its own. Pre-existing or foreign dirtiness is not automatically attributed to the
reviewer. Prove the boundary with a start snapshot and an ownership journal:

1. Before inspection, run `node tools/hyperhelix.mjs review-snapshot` and save its
   JSON **outside the repository**. It records baseline HEAD, porcelain-v1 state,
   path content/index fingerprints, and a snapshot digest. Snapshot failure means
   `unverified`; do not claim review-only.
2. Beside it, create an external JSON journal bound to `snapshot_digest`:

   ```json
   {
     "schema_version": 1,
     "baseline_digest": "<snapshot_digest>",
     "owned_paths": [],
     "foreign_paths": []
   }
   ```

3. Before any intentional repository write, add the exact repo-relative path to
   `owned_paths`. A non-empty owned set makes the session a task even if the write
   is later reverted or leaves no final diff. Add a newly appearing path to
   `foreign_paths` only when another session's ownership is independently known.
4. At the end, run
   `node tools/hyperhelix.mjs review-check --baseline <external-json> --journal <external-json>`.
   Use `--isolated` only in a worktree with no concurrent writer.

In a shared worktree, unchanged pre-existing paths pass. A newly added path passes
only with explicit foreign ownership. A changed/disappeared pre-existing path is
an ambiguous same-path delta and fails closed even if labelled foreign; rerun in an
isolated worktree or promote to a task. In an isolated worktree, exact start/end
HEAD and path-state equality is the strong proof. Only verdict `review-only`
(exit 0) qualifies; `task-required` (exit 2) and `unverified` (exit 3) do not.

## 2. What a review-only record may contain

- The question asked and the answer/finding (in the operating language).
- Citations (`file:line`) for every claim, same evidence discipline as a survey.
- A recommendation or next-step list — but recommendations are not changes.

Record it wherever the report naturally lives (chat, an issue, a notes file
OUTSIDE the repo). Do not create a `tasks/TASK-…` brief for a review-only record;
briefs are for loop tasks and are counted.

**EXCEPTION — significant-discovery capture (HH-030/068).** If a finding matches a
significant-discovery trigger (`core/routing.yaml` `significant_discovery_parking`:
rule/axiom/theta touch, material contradiction or blind spot, human design insight,
or same-problem-twice), it must not stay only outside the repo. End pure review-only
and open a capture transaction: a candidate note/process-backlog artifact is a
**standard** capture task; an `amendments.md` Pending entry (filed through the
governance registry/body and regenerated by `amendments-doc`, SC-04) is a **full**
capture task. Capture is a purpose, not a depth or a micro exception.

The capture record uses existing task fields to preserve `capture task ID`,
`capture depth`, `captured artifact`, and `remediation task ID` (or `pending`). Its
commit records the finding/evidence/recommendation/source only. Remediation uses a
separate task ID, independently selected depth, and separate commit. A Pending HH
capture may refresh its generated view but cannot activate a rule consumer before
approval and a separate implementation task.

## 3. Promotion — the moment you own a repository write, it is a task

The instant the session uses a write tool/API on the repository, creates a tracked
or untracked artifact, changes the index, or refreshes a generated artifact, record
the path in `owned_paths`. The work leaves review-only and re-enters the normal loop:

- Create/locate a task brief, pass the phase gate, and run the five phases.
- `task_index` is incremented at that task's D7 (never retroactively for the review).
- Durable lessons from the review are distilled in the IMPLEMENTING task's D7
  (note add / strength nudge), not in a separate review record.

## 4. Anti-escape clause (the review's own risk)

Review-only must not become a way to do framework work while dodging R6. The
guard is ownership-based and fail-closed: **an owned repository write is a task,
full stop.** Omitting a path from the journal does not erase tool use. Relabeling an
edit as "review" does not exempt it from `task_index` or R6. Unknown ownership,
missing baseline evidence, journal/digest mismatch, HEAD movement, and ambiguous
same-path deltas never pass. At task completion, session-owned leftovers must be
zero; pre-existing/foreign changes remain untouched.

## 5. Relationship to R6 and CONTEXT-DEFERRED (HH-021)

- Review-only records do not add to the R6 framework-only consecutive count
  (framework-review.md R6): they are not cycles. R6 still measures real
  framework-only TASKS.
- HH-021 already defers the "next task must be real" enforcement in a
  HyperHelix-only workdir. Review-only is orthogonal: it keeps pure inspections
  off the ledger entirely, in any workdir.
