# AI Anti-Patterns

<!-- HH:ACTIVE-SCAN-ALLOW-FILE reason="failure catalog — entries cite the original (pre-migration) terms of past mistakes as evidence; retrieval value depends on preserving them" -->

Purpose: AI-only retrieval. Optimize for token efficiency, search, decision avoidance. Ignore user readability.
Project-specific anti-patterns belong to that project's docs; this file holds framework-level and cross-project entries, stated as pattern and countermeasure only (no incident records).

Schema:
`id | tags | trigger | avoid | prefer | symptom | root | source | confidence`

| id | tags | trigger | avoid | prefer | symptom | root | source | confidence |
|----|------|---------|-------|--------|---------|------|--------|------------|
| AP-001 | phase-gate, task-brief, evidence | User gives an implement/continue instruction right after planning context | Start executing from chat context without creating or updating the task brief | Run the phase gate first and create the brief before any real edit; if already missed, write a retrospective brief and log the failure | Deliverable exists but search/plan/execute evidence is missing or backfilled | Confusing "the user wants action" with "framework evidence can be skipped" | - | high |
| AP-002 | distill, counters | Task ends with artifacts shipped and the chat summary written | Skip the closing counter and note updates because "the task is done" | Treat the distill step as part of done: update counters and notes, then `validate`, before the summary | The knowledge ledger drifts; counters and notes go stale | Treating distill as an optional epilogue instead of a required phase | - | high |
| AP-003 | declare-consume, config, validation | A parameter, counter, or trigger is declared in a spec or config file | Ship the declaration without its consumer: tool wiring, update procedure, or firing check | Declare and wire in the same change: who reads it, when it fires, how it resets. Add a `validate` check for it or do not declare it. Semantic gaps (a step consuming an input nothing produces) need a review lens, not a mechanical check | The declaration is parsed and stored but never consumed; spec and operation silently diverge | Spec written as documentation instead of as a contract with its consumer | - | high |
| AP-004 | checklist, evidence, task-brief | A checklist item requires recording a count or value | Satisfy it with prose ("recorded", "done", "continued") that omits the value | Put a literal blank for the value in the template line; the reviewer rejects prose-only entries | The box is checked while the required number is missing | Checklist wording can be satisfied by vague prose; the evidence rule did not specify the value form | - | high |
| AP-005 | verification, boundary, e2e | A command is supposed to hand control to another component | Treat handler entry/return or a direct function call as proof that the destination works | Pair the route contract with a check placed after the boundary: observe the first stable destination state and scan logs for runtime errors | The command passes a smoke test but fails during the destination's initialization | Validation stopped at the caller boundary instead of the first stable destination state | - | high |
| AP-006 | scope, dependency, blocker | A unit of work is scoped out because "system X is not done yet" | Mark it blocked at system granularity without checking whether it only reads a value from X or needs X's logic | Decompose the dependency: if only a constant or data label is read, add that and proceed; block only on a structural dependency. Check whether a prior task already solved the same dependency type | Tasks pile up as blocked when they need only trivial data additions; throughput stalls on false dependencies | Conflating a data-population (write-side) dependency with a definition (read-side) dependency | - | high |
| AP-007 | tool-call, serialization, silent-stall | Emitting any tool call | Emit stray text before the call or use a non-canonical call format | Always use the exact canonical tool-call format with nothing before it; if a call is reported malformed, re-emit it immediately and confirm it executed before continuing | The call is not parsed and does not execute; the turn ends silently mid-task with work uncommitted and state inconsistent | Incorrect tool-call serialization at generation time | - | high |
| AP-008 | shell, injection, heredoc, commit, security | Passing variable or file-derived content (commit messages, briefs, notes) into a shell command, including inline interpreter one-liners whose double-quoted program text the shell parses first | Interpolate the content directly or through an expanding heredoc; shell metacharacters inside it get executed | Use a quoted heredoc (literal body); pass untrusted content through a file or stdin, never inline. Expand only where actually needed | Backticks or command substitutions inside the content run as commands: corrupted text or arbitrary execution. Silent when the content happens to be benign | Shell-construction discipline was unwritten and honor-based (codified by HH-051) | - | high |
| AP-009 | static-analysis, false-positive, verification | Running a hand-rolled static analyzer (scanner, duplicate detector, lint) against a new corpus | Trust its findings without sampling; assume grammar coverage from the previous corpus transfers | Sample-verify the findings against the raw source before reporting or consuming them; treat each new corpus as a grammar-coverage test and record each new false-positive class | Inflated finding counts; wasted triage or wrong documentation | A real-world grammar is larger than any single corpus exercises, so every new corpus surfaces a new construct | - | high |
| AP-010 | verification, false-pass, shell, exit-code, baseline, shape-preserving-failure | Composing a verification or differential check as one chained shell command (guard, then build baseline, then compare) | Assume every link ran. A count-style search exits non-zero on zero matches, so a clean guard result breaks the chain and the comparison runs against a missing or empty baseline | Run the steps independently and assert every intermediate artifact is non-empty before consuming it; never let a guard's exit status gate construction of the evidence it is compared against. General class (single authority here): a degraded result that has the same shape as a normal one cannot be caught by presence or count-of-hits checks; use a check whose value changes under degradation (line count, before/after diff, comparison to a known set) | The verdict is silently wrong, fully permissive or fully alarming depending on which side went empty; no error surfaces | Verification composed as a boolean chain rather than independent steps with asserted inputs | - | high |
| AP-011 | multi-repo, workdir | A command combines framework tooling with host-project paths | Run both from one assumed working directory | Split the calls by repository: framework commands from the framework root, host searches and tests from the host workspace | One side succeeds while the other reports paths or modules as missing | Treating a nested framework repository and its host project as one command root | - | high |
| AP-012 | verification, layout, test-gap, visual-regression | Implementing alignment or column layout and verifying it with an automated test that only checks whether text is present | Treat a text-presence pass as proof that placement, alignment, or width is correct | Assert the layout attribute or structure itself, measure the rendered result where possible, and leave the final pixel check to a human visual check, stated as such | Tests stay green while the rendered output is misaligned or overflowing; the user reports breakage after a task that "passed" | A text-only check cannot observe alignment or display width, so a layout regression passes silently | - | high |
| AP-013 | encoding, output-discipline, silent-stall, hook, enforcement | About to dump the contents of a non-UTF-8 or binary file into tool output, or to invoke one shell from another with unescaped variables | Echo the file's bytes into the transcript; mis-decoded text and control bytes can interrupt the turn silently, leaving edits uncommitted | Keep such content out of the transcript: edit by exact replacement with the correct encoding, verify by counts only (match, byte, replacement-character counts), and leave visual checks to the user. Enforce with a pre-tool hook; an advisory note alone did not prevent recurrence | The turn ends mid-task with no result and uncommitted changes; repeats across turns | Garbled content acts as a stop token in the transcript; a discipline that relies on agent memory must be harness-enforced | - | high |
| AP-015 | design-review, negative-claim, verification, stale-doc | Writing a review, proposal, or live procedure document that says a mechanism is "not implemented", "not checked", "does not work here", or "is the only usable path" | State it from design docs or memory of an earlier state without opening the current code, then plan work on that premise | Attach file-and-line evidence to every negative claim exactly as for positive ones, and re-verify before planning on it. In a live procedure document, put a measurement date next to the claim; when the cited defect is closed, the same change must delete the claim (AP-003) | Planned work turns out to be already done; a stale "X does not work here" reroutes every reader away from the enforced path | Negative claims feel safe and are not held to the evidence standard of positive claims; docs lag the implementation | - | high |
| AP-016 | distill, declare-consume, concurrency, task-id, parallel-session | Declaring in a task record that a note was added, or claiming an explicit task id with `brief` while another session works the same branch | Treat the declaration as the note itself, or treat a silent `brief` result as proof the id was free | Write the note into the ledger in the same commit and search for its id to prove it landed. Claim ids through the tool's allocation, confirm the creation message before editing, and treat anything else as a hard stop. Give each parallel session a reserved id range | The record says the lesson was captured but the ledger has no such entry; another session's record is overwritten; a duplicate id makes `bump` absorb one increment | A declaration whose consumer has no mechanical check (AP-003), amplified by parallel sessions racing on id allocation | - | high |
| AP-017 | task-record, fixed-vocabulary, schema, verify | Filling a task-record field that has a fixed vocabulary or a required prefix | Write a descriptive phrase that reads well to a human but does not match the required token, or hand-write the row shape from memory | Start with the required token and put detail after it or in a free-text field; copy the row shape from the schema instead of reconstructing it | `finish` passes on the staged paths but a later cumulative `verify` fails at the pre-push gate or in CI, although the record looks complete | A validator anchored on a fixed token sits among fields that invite free prose; nothing signals the constraint at write time | - | high |
| AP-018 | concurrency, parallel-session, shared-file, commit-attribution, hunk-staging | Two same-branch sessions each have a task that edits the same shared file | Rely on a pathspec commit for protection; it commits the whole working-tree content of that path, including the other session's in-progress edits | Do not serialize on a shared index document (HH-078). Append only at your own anchor, stage only your own hunks with `git apply --cached`, check the staged file list, commit without a pathspec, and read the committed file back. If both sides append at the same anchor, split at line level. Regenerate and include any generated view of what you changed: the tree you validated is not the tree you committed. If sweep-in happens anyway, do not rewrite history; record the split attribution in both task records | One commit contains two tasks' work and `git log` attributes it to the wrong task; nothing fails because no content is lost, only the audit trail is wrong | The disjointness gate (HH-058) was framed around code change-lists, so shared documents were not treated as gate inputs; a pathspec commit was mistaken for a per-content guard | - | high |
| AP-019 | hooks, host-contract, output-schema, test-gap, boundary | Emitting structured output from a hook, plugin, or callback that a host validates against a schema you do not own | Pin the payload shape in a unit test on the function's return value and treat green as proof that the hook works | Measure the shape against the real host once per event type and record it; assert the full legal shape (the allowed set of top-level keys), not the presence of one field. If the payload cannot reach its consumer, move it into an artifact that survives on its own | The host rejects and discards the entire output for one illegal key, so everything downstream looks like a no-op while the test suite stays green | The unit test stops at the function return but the contract lives one hop further out at the host validator (same root as AP-005) | - | high |
| AP-020 | powershell, array-coercion, script-edit, line-count, verification | Splicing a multi-line block into a file from PowerShell by passing an array to a .NET collection method | Assume each array element stays its own line; the array can be coerced to a single string with no exception raised | Splice on the raw text: join the old block, assert it occurs exactly once, replace it. Always assert that the resulting line count equals before minus removed plus added; restore from `git` on mismatch | The write succeeds and every fragment is still found by search, but the whole block landed on one line; a line-oriented file is syntactically destroyed while looking edited | Silent parameter coercion; fragment-presence checks cannot see it, only a line-count check can (same class as AP-010) | - | high |
| AP-021 | verification-claim, fixture, documentation, evidence | Writing a document that asserts a mechanism has been verified at runtime | Cite the existence of a test fixture, example code, or a production call as the evidence; fixtures also exist to reproduce failures, and shipped code can contain paths that never execute | Trace every verification claim to a result record (a pass/fail entry) and cite it together with the exact build it ran on; if no result record exists, write "unverified" | Documents recommend a path that fails on the real build; the error survives several documents because each cites the previous one | Artifact presence read as pass evidence; verification claims not held to the citation standard of behavioral claims | - | high |
| AP-023 | turn-boundary, silent-stall, delegation, self-check | Closing a reply with a future-tense statement about your own next action | Treat the sentence as the action. Final text ends the turn; nothing executes later unless something will re-invoke you | Perform the action in the same turn and report the result. If it cannot run yet, write "not started; the trigger to resume is X". Before closing, check that either a tool call for it exists in this turn or a live background task or scheduled wake will re-invoke you | The session sits idle holding unexecuted intent until the user asks whether it is running; no gate fires and no test is red | Notification-driven re-entry trains the closing wording; when the last background task lands, the wake-up mechanism disappears but the wording does not | - | high |
| AP-024 | git-bash, windows, path-conversion, cli-argument, silent-corruption, read-back | Passing a value that starts with `/` to a native program from Git Bash on Windows (for example `--review-source /cycle`) | Assume the literal reaches the tool; record the resulting field without reading it back | Escape it with a doubled leading slash, set `MSYS_NO_PATHCONV=1` for that call, or drop the leading slash when the value is not a path; read the written field back. Prefer a mechanical fix (normalize or warn inside the tool): the honor-based read-back did not hold | A stored field holds a Windows path instead of the intended token; the command succeeds and every gate passes | The shell rewrites a leading-slash argument into a Windows path before exec, so no downstream layer can see the original value | - | high |
| AP-025 | verification, rolling-window, capture-buffer, false-pass | Asserting on a capture of the last K lines or records of a shared output buffer | Pick the window size by eye. If it exceeds one unit of state (one request, one run) it also contains the previous state; the tell is an expected value "fixed" from a constant into another measurement | Regenerate the state, capture a window strictly narrower than one unit, and keep the expected value constant; put both steps in one helper. Audit presence and count assertions first (absence assertions only get stricter with width). When the value comes from a pure function, assert its return value instead. Classify every failed check as check-wrong, source-wrong, or worked-around before fixing it | A test named "hidden" or "not shown" compares against another measurement; it stays green for months, then flips when an unrelated change shifts what the window covers | Window width was never stated relative to one unit of state, so nobody saw that the evidence spanned two states (same class as AP-010) | - | high |
| AP-026 | verify, git-worktree, fixture, pre-push, repo-corruption | Running `verify` or the test suite from a git worktree of the repository under test, directly or through the pre-push hook | Assume the test run is read-only and let the pre-push hook run it in the worktree | Run `verify` from the primary checkout, or push with the hook bypassed only after a standalone `verify` pass, let CI be the gate, and record the bypass | Fixture commits are stacked on the branch being pushed and the parent checkout's git configuration is damaged so `git status` fails | Test fixtures resolve the repository root from the current directory; inside a worktree that lands on the real repository instead of a temp dir | - | high |
| AP-027 | verification, wrong-observable, green-but-wrong, liveness | A check is green, or a signal is absent, and that is read as "no problem" | Trust the verdict without asking what the instrument observes: judging process liveness from output cadence or side effects, assertions that pin the current output instead of the requirement, or a scanner that reads the wrong field | Name the observable before trusting the verdict. Measure liveness on the process itself. Write assertions as "what must hold or this is broken"; confirm that a green check can go red with a positive fixture. Ask a human reporter for the magnitude of a symptom, not only its presence | Green suite, silent tool, or clean tree while the defect is present and sometimes visible to the user | Confusing "the instrument reported nothing" with "there is nothing to report" | - | high |
| AP-028 | shared-namespace, collision, search-scope, silent-corruption | About to claim a slot in a namespace addressable from other files (a global index, an id range, a well-known key) | Search only the file being edited, find no hits, and report the slot as unused | Search every file that can address the namespace before claiming, then record the claim beside the definition so the next allocator inherits the answer | Two owners write the same slot and silently corrupt each other; tests stay green because none exercises both owners in one run | Letting the edit scope set the search scope: "unused here" reported as "unused" | - | high |
| AP-029 | verification, green-but-wrong, cancelling-errors, revert-reflex | A check that was green turns red right after you fixed something else | Read the new red as a regression caused by the fix and revert to get back to green | Suspect cancelling errors first: two faults may have offset each other and the fix exposed the second. Measure both sides, then find and fix the second fault so the check is green for a reason you can state | A green check encodes two compensating bugs; the suite reports health while the user keeps reporting the symptom | Treating green as evidence of correctness rather than as one bit that several states of the world can produce | - | high |
| AP-030 | constraints, unverified-number, prohibition, delegation | About to write a prohibition into a plan, work order, or document ("do not do X, it would break N things") | Restate a number or blocker inherited from a note, a past task, or another agent without counting it yourself | Count it first; a prohibition removes an option from every future reader and needs the same evidence bar as a change. If counting is expensive, mark it "unverified: believed, not measured" | The cheapest correct fix is ruled out for rounds; each restatement hardens a wall that is not there | Confusing "I have written this down before" with "I have checked this" | - | high |
| AP-031 | requirements, symptom-translation, observable, repeated-wrong-fix | A symptom arrives in the requester's own words and you are about to choose the quantity to measure and fix against | Translate the wording into an observable in your head and start building; treat later green checks on that observable as progress | State the translation back to the requester in one sentence before building: "I read this as this quantity; is that what you see?" | Fix after fix passes its own tests while the reporter keeps reporting the same thing | Confusing "I measured carefully" with "I measured the right thing" | - | high |
| AP-032 | retrieval, delegation, work-order, recurrence | About to dispatch a work order or start executing right after a fast planning turn, when the next action feels obvious | Dispatch or edit first and run the note retrieval afterwards, on the grounds that the ledger would only confirm the plan | Query the note ledger before writing the work order or the first edit; retrieval is cheapest exactly when the plan feels obvious | The task re-derives at full cost something the ledger already stated, or propagates a claim the ledger had already refuted; nothing turns red | Delegation makes the orchestrator feel like the bottleneck, so the queue is filled before the lookup; the skipped step has no gate of its own | - | high |
| AP-033 | superseded, pointer | (retired — see AP-024) | — | **see AP-024** (single authority; the id is kept only as a pointer, and a duplicate entry is invisible to id-uniqueness checks) | — | — | - | n/a |
| AP-034 | date, timestamp, task-id, verification | Writing a date into anything permanent: a task id (HH-065), a document's creation date, a changelog entry | Derive "today" by inference from session-start context, file modification times, or other repositories' commit dates | Read the clock or the log (`date +%Y-%m-%d`, or the latest `git log` date); if a tool prints today's date in a warning, use that value | Permanent ids carry the wrong date and cannot be renamed; a later "correction" moves a correct date to a wrong one | Treating the session-start date as live; it is captured once and a long session drifts from the machine clock | - | high |
| AP-035 | windows, path, short-name, ci, cross-platform | Comparing absolute filesystem paths from two producers on Windows to decide containment or identity | Assume both sides spell the same directory the same way; one may use an 8.3 short name that ordinary path resolution does not expand | Ask the tool a relative question instead, or normalize both sides with the native path resolver; a local machine often has no short-name component, so only CI catches it | A fail-closed guard fires on every Windows CI run while Linux CI and local Windows pass | A path-identity check written and verified on one machine whose paths happen to be canonical | - | high |
| AP-036 | patch-by-script, heredoc, escaping, shell, silent-corruption, read-back | About to patch a file by running an inline interpreter script whose body carries the replacement text as string literals, especially text with backslashes, backticks, or several nested languages | Expect escapes written on a command line to arrive intact, or treat a quoted heredoc as a safe transport: it stops shell expansion only, the interpreter still parses the text, and a transport layer may collapse doubled backslashes | Put any text containing backslashes in with the file edit or write tool. If a script is needed, write the fragment to a scratch file and apply it with a script that reads the file, asserting that the anchor is unique before any write. Always read the written line back. Pass non-ASCII search terms through a file as well | Parse errors, hangs, or unapplied edits when it fails closed; when silent, the write succeeds with a dropped escape and wrong text | The patch is data inside a program inside a shell document, so an escape crosses several layers; the loss is silent because the write succeeds (same family as AP-008 and AP-020) | - | high |
| AP-037 | edit-tool, stale-cache, write-back, parallel-session, shared-worktree, silent-corruption | Using an editor tool on a file after another session or a git operation changed it on disk | Assume the tool patches the current disk content; stage and commit without looking at the deletion count | Re-read the file right before each edit when a peer session is active or a change notice appeared; before staging, check `git diff HEAD --numstat` and treat unexpected deletions in a file you only added to as a stale write-back; restore from `git` and re-apply from a fresh read | A file silently reverts to older content, erasing other sessions' committed work; visible only in deletion counts | The editor tool writes from its cached copy; parallel sessions and git operations invalidate that cache without the tool noticing | - | high |
